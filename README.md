# Миллионика

Браузерная RPG на Next.js + TypeScript, ASP.NET Core на .NET 10 и PostgreSQL 18.

## Текущее состояние

Реализованы регистрация и серверные сессии, персонаж и прогрессия, контракты, Взлом, тренировки, магазин, инвентарь и экипировка, охота на роботов с пошаговым боем, закрытая админка, публичные профили, друзья и заявки. Бой охоты сохраняется в PostgreSQL и продолжается после обновления страницы или перезапуска сервера. Сообщений, синдикатов, чата, PvP и рынка игроков пока нет.

Проект предназначен для локального запуска. Ограничения до публичного размещения перечислены в [архитектуре](docs/ARCHITECTURE.md#ограничения) и [отчёте проверки](docs/REVIEW.md).

## Быстрый маршрут нового разработчика

1. Выполните шаги [первого запуска](#первый-запуск), затем запустите backend и frontend по разделу [Запуск](#запуск).
2. Начните с [ARCHITECTURE](docs/ARCHITECTURE.md): там карта модулей, сущностей, транзакций, requestId и миграций. Фактическая готовность указана в [STATUS](docs/STATUS.md), игровые правила боя — в [COMBAT_SPEC](docs/COMBAT_SPEC.md), общий план — в [MILLIONIKA_MASTER_PLAN](docs/MILLIONIKA_MASTER_PLAN.md).
3. Для проверки кода создайте отдельную базу `millionnika_tests`, задайте `MILLIONNIKA_TEST_CONNECTION_STRING` и выполните полный прогон из раздела [Тесты — только на отдельной базе](#тесты-только-на-отдельной-базе). Рабочая база `millionnika` валидатором тестов запрещена.

Подробные документы: [главный план](docs/MILLIONIKA_MASTER_PLAN.md), [архитектура](docs/ARCHITECTURE.md), [текущий статус и история этапов](docs/STATUS.md), [правила боя](docs/COMBAT_SPEC.md), [проверка и известные ограничения](docs/REVIEW.md), [ТЗ прототипа](docs/PROGRAMMER_SPEC_MVP.md), [ТЗ экипировки](docs/TASK_EQUIPMENT_TORN.md) и [сверка экипировки с Torn](docs/EQUIPMENT_TORN_NOTES.md).

## Первый запуск

Откройте PowerShell в папке проекта:

```powershell
cd "D:\Unity Work\Millionnika"
npm ci --prefix frontend
dotnet restore Millionnika.slnx
.\scripts\Setup-Database.ps1
```

Последняя команда один раз запросит пароль администратора PostgreSQL. Она:

- создаст отдельную базу `millionnika`;
- создаст пользователя `millionnika_app` без административных прав;
- сгенерирует пароль приложения и сохранит его вне проекта в .NET User Secrets;
- проверит реальное подключение.

Пароль не записывается в репозиторий и не выводится на экран.

Скрипт ожидает PostgreSQL в `D:\PostgreSQL\18\bin`; для другого места укажите `-PostgreSqlBin`. Повторный запуск меняет пароль существующей роли приложения — для обычного запуска его выполнять не нужно.

Откройте два окна PowerShell.

Окно 1 — сервер:

```powershell
cd "D:\Unity Work\Millionnika"

```

Окно 2 — сайт:


Откройте [http://localhost:3000](http://localhost:3000). На странице должны быть зелёными статусы сервера и базы. Для создания игрока нажмите «Создать персонажа».

При первом запуске backend автоматически применяет все отсутствующие миграции — от исходных аккаунтов до охоты и переименования боевых характеристик. Пароли сохраняются только в виде безопасного хеша.

## Создание первого администратора

Остановите backend и выполните локально:

```powershell
cd "D:\Unity Work\Millionnika"
dotnet run --project backend\Millionnika.Api -- --create-admin
```

Команда запросит имя, email и пароль. При вводе пароль не показывается, не выводится в журнал и сохраняется только как безопасный хеш. Готовые пароли в коде и базе миграций отсутствуют. После создания снова запустите backend обычной командой и войдите через `/login`; администратор будет направлен в `/admin`.

После входа откройте профиль:

- «Контракты» — выполнить «Перехват рекламного дрона»;
- «Взлом» — посмотреть уровень навыка и доступные цифровые задачи;
- «Имплант-центр» — выбрать и улучшить одну характеристику;
- «Магазин» — купить расходники или отдельные экземпляры оружия/брони;
- «Инвентарь» — использовать расходники, надеть, заменить или снять экипировку;
- «Активности» → «Охота» — выбрать робота и провести сохраняемый пошаговый бой;
- «Игроки» — найти игрока и открыть его публичный профиль;
- «Друзья» — принять, отклонить или отменить заявку и управлять списком друзей;
- результат действий и новые значения сразу возвращает сервер.

У расходника может быть серверное ожидание после применения: `cooldownSeconds` и `cooldownGroup` задаются администратором. Значение `0` отключает ожидание; расходник с ожиданием применяется только по одной штуке. Предметы одной группы делят таймер для одного персонажа. Инвентарь показывает оставшееся время; решение о доступности принимает сервер. Старые расходники по умолчанию имеют `0` секунд.

Победа в охоте может дать дополнительный диапазон кредитов и предметы. В текущем примере «Сторожевой паук» независимо разыгрывает металлолом (60%, 1–2), компоненты (15%, 1) и «Искру» (0,001%, 1). Материалы складываются в инвентаре, оружие/броня выдаются отдельными экземплярами. Продажи и передачи материалов пока нет. Администратор настраивает диапазон и строки добычи у каждого робота; шанс задаётся с точностью до 0,001%. Дополнительные кредиты прибавляются к прежней награде, существующий опыт Охоты не меняется.

Каталог НПЦ: войдите администратором и откройте `/admin` → «НПЦ» → «Мирные», «Роботы», «Мутанты» или «Животные». Там можно создавать и редактировать шаблоны с обязательной причиной. Три охотничьих робота видны в подразделе «Роботы» и редактируют те же записи, что использует охота. В «Активности → Охота → Локации» выберите локацию: там видны назначенные НПЦ, кнопки «Добавить» и «Убрать». При первом назначении нового боевого шаблона администратор явно задаёт стоимость, уровень, боезапас и награды; впоследствии один и тот же НПЦ назначается в другие локации без повторного задания характеристик. Снятие назначения не удаляет НПЦ и не прерывает начатый бой. Поля портрета и фигуры принимают HTTPS-ссылку или путь от `/`; без них показывается текстовая заглушка. Загрузка изображений, торговля и диалоги не реализованы.

Энергия восстанавливается на 5 единиц каждые 15 минут, хладнокровие — на 1 единицу каждые 5 минут. Значения ограничены максимумом. В профиле показано время до следующего восстановления, а для полного ресурса — «Полностью восстановлено». Здоровье пока автоматически не восстанавливается.

Восстановление считает backend по серверному времени UTC и сохранённым отметкам в PostgreSQL. Поэтому оно работает при закрытом браузере и после перезапуска приложения. Отдельные постоянно работающие таймеры для игроков не создаются.

### Тесты — только на отдельной базе

Интеграционные тесты требуют отдельную переменную `MILLIONNIKA_TEST_CONNECTION_STRING`. Они не читают User Secrets и игнорируют `ConnectionStrings__GameDatabase`. Без настройки или при недопустимой базе запуск завершается ошибкой до подключения и миграций.

Разрешены только localhost/127.0.0.1/::1, непустой пользователь (не postgres), база `millionnika_tests` либо `millionnika_tests_<суффикс>` из строчных латинских букв, цифр и разделителей `_`. Рабочая база `millionnika` запрещена. Подготовьте отдельную базу один раз (пароль PostgreSQL вводится по запросу, не в командной строке):

```powershell
& "D:\PostgreSQL\18\bin\psql.exe" -X -W -h localhost -U postgres -d postgres -v ON_ERROR_STOP=1 -c "CREATE DATABASE millionnika_tests OWNER millionnika_app;"
```

Если база уже существует, создание пропустите; сбрасывать её не нужно. Следующий пример явно собирает отдельную тестовую строку из локальной настройки доступа, заменяя имя базы. Это ручная настройка окна PowerShell, а не fallback тестов. Секрет не выводится:

```powershell
cd "D:\Unity Work\Millionnika"
$testSettings = Get-Content (Join-Path $env:APPDATA "Microsoft\UserSecrets\millionnika-api-development\secrets.json") -Raw | ConvertFrom-Json
$testConnection = $testSettings.'ConnectionStrings:GameDatabase' -replace '(?i)(^|;)Database=[^;]*', '$1Database=millionnika_tests'
if ($testConnection -notmatch '(?i)(^|;)Database=millionnika_tests(;|$)') { throw "Тестовая база не выбрана" }
$env:MILLIONNIKA_TEST_CONNECTION_STRING = $testConnection
try {
    dotnet test Millionnika.slnx --no-restore
} finally {
    Remove-Item Env:MILLIONNIKA_TEST_CONNECTION_STRING
}
$testConnection = $null
$testSettings = $null
```

Общая xUnit fixture сама применяет миграции один раз до всех интеграционных тестов. Запускать backend для подготовки схемы больше не нужно. Тестовые классы одной коллекции выполняются последовательно; параллельные запросы через Task.WhenAll внутри тестов сохранены. Для одновременных отдельных процессов тестирования выбирайте разные тестовые базы.

Тесты создают и очищают только свои записи в выбранной базе. Не используйте в ней реальные аккаунты. Кроме правил и сервисов, HttpSecurityTests запускает настоящий backend на свободном loopback-порту, проверяет HTTP-маршруты и middleware, затем останавливает его. Строка подключения дочернего процесса обязательно проходит тот же тестовый валидатор; рабочие настройки не используются. Подробности результатов — в REVIEW.

## Реализованные API

- `POST /api/auth/register` — регистрация и создание персонажа;
- `POST /api/auth/login` — вход по имени или email;
- `POST /api/auth/logout` — выход;
- `GET /api/auth/session` — проверка текущей сессии;
- `GET /api/auth/csrf` — получение CSRF-токена и защитной cookie перед изменяющим запросом;
- `GET /api/profile` — профиль только текущего авторизованного игрока;
- `GET /api/game/contracts?direction=normal|hacking` — обычные контракты или задачи Взлома с доступностью для текущего игрока;
- `POST /api/game/contract/execute` — выполнить выбранный контракт (`requestId`, `contractId`);
- `GET /api/game/training` — серверные параметры тренировки;
- `POST /api/game/training/execute` — тренировать разрешённую характеристику;
- `GET /api/game/logs` — последние игровые действия текущего игрока;
- `GET /api/game/shop` — активные товары NPC из PostgreSQL;
- `POST /api/game/shop/buy` — атомарная покупка предмета;
- `GET /api/game/inventory` — инвентарь текущего игрока;
- `POST /api/game/inventory/use` — использование предмета;
- `POST /api/game/inventory/equip` и `/unequip` — надеть экземпляр в разрешённый слот или снять вещь;
- `GET /api/game/hunting/locations` — доступные локации и цели охоты;
- `GET /api/game/hunting/fight` — текущий или последний бой;
- `POST /api/game/hunting/start` и `/turn` — начать охоту, атаковать или перезарядить оружие;
- `GET /api/admin/players` и `GET /api/admin/players/{id}` — игроки и профиль персонажа;
- `PUT /api/admin/players/{id}/block` — блокировка или разблокировка;
- `PUT /api/admin/players/{id}/resources` — изменение ресурсов с обязательной причиной;
- `GET/POST /api/admin/contracts` — просмотр и создание контрактов;
- `PUT /api/admin/contracts/{id}` — редактирование или отключение контракта; удаления нет;
- `GET/POST /api/admin/items` — просмотр и создание определений предметов;
- `PUT /api/admin/items/{id}` — изменение цены, описания, параметров, покрытия и активности с аудитом;
- `GET /api/admin/action-logs` — журнал игровых действий;
- `GET /api/admin/audit-logs` — журнал изменений администратора;
- `GET /api/admin/hunting/locations` и `/hunting/targets` — просмотр настроек охоты;
- `PUT /api/admin/hunting/locations/{id}` и `/hunting/targets/{id}` — изменение охоты с обязательной причиной и аудитом;
- `GET /api/players?query=&page=1&pageSize=20` — поиск незаблокированных игроков;
- `GET /api/players/{id}` — публичный профиль без приватных игровых данных;
- `PUT /api/players/{id}/description` — изменение только собственного описания;
- `GET /api/friends?list=friends|incoming|outgoing&page=1&pageSize=20` — личные списки друзей и заявок;
- `GET /api/friends/status/{playerId}` — состояние отношений с игроком;
- `POST /api/friends/requests` — отправка заявки;
- `POST /api/friends/requests/{id}/accept` и `/reject` — решение по входящей заявке;
- `DELETE /api/friends/requests/{id}` — отмена исходящей заявки;
- `DELETE /api/friends/{id}` — удаление дружбы;
- `GET /api/health` — состояние backend и PostgreSQL.

Сессия связана с записью `user_sessions` в PostgreSQL и защищённой HttpOnly-cookie. Срок — 7 дней без автоматического продления. Имя, email и пароль повторно проверяются сервером; одинаковые имена и email запрещены.

Все адреса `/api/admin/*` требуют серверную роль `Admin`. Обычный игрок получает HTTP 403. Выход удаляет текущую сессию на сервере, сохраняя остальные входы. Блокировка запрещает вход и удаляет все сессии пользователя в одной транзакции. Разблокировка не оживляет старые cookie: требуется новый вход. Штатные DTO админки не возвращают пароли или их хеши; необработанная ошибка API возвращает безопасное сообщение и `errorId` без stack trace, cookie, заголовков и локальных путей.

### CSRF и временные лимиты

Все методы, кроме GET/HEAD/OPTIONS, проходят серверную antiforgery-проверку, включая регистрацию, вход, выход и заявки без тела. Frontend использует общий `apiFetch`: перед изменением получает свежий токен с `/api/auth/csrf`, затем отправляет его в `X-CSRF-Token` вместе с cookie. Токен не сохраняется в localStorage и не выводится в журнал. Для ручных API-клиентов нужны те же два шага с общей cookie-сессией. Нет/неверен токен — HTTP 403 с кодом `csrf_invalid`. CORS остаётся отдельной настройкой доступа из браузера.

В `backend/Millionnika.Api/appsettings.json`, секция `AuthProtection`:

| Параметр | По умолчанию |
| --- | --- |
| LoginIpLimit | 30 попыток входа с одного IP |
| LoginNameLimit | 10 попыток на нормализованный логин |
| RegistrationIpLimit | 5 попыток регистрации с одного IP |
| WindowSeconds | 60 секунд на окно |
| MaxBuckets | 10000 одновременно учитываемых ключей |

Учитываются и успешные попытки. IP-лимит действует также на неверные запросы до проверки CSRF. Логин приводится к верхнему регистру с удалением пробелов по краям; одинаковое написание в разном регистре не обходит лимит. Ответ 429 содержит понятное сообщение, `retryAfterSeconds` и заголовок `Retry-After`. Постоянная блокировка аккаунта лимитером не устанавливается. IP берётся из соединения; произвольный `X-Forwarded-For` не принимается за адрес клиента.

Ограничения: счётчики лимитов находятся в памяти одного процесса и сбрасываются при перезапуске. Несколько экземпляров пока имеют отдельные счётчики — до масштабирования потребуется общее хранилище/лимитер на входном прокси. За прокси без специально настроенного доверия адресом будет сам прокси. Для cookie и CSRF между экземплярами нужны общие защищённые Data Protection keys и одинаковый application discriminator, а также общая PostgreSQL. Отзыв сессий хранится в БД и переживает перезапуск; запрос, уже прошедший проверку до отзыва, может успеть завершиться. Истёкшие строки сессий отклоняются, но их периодическая очистка пока не автоматизирована.

### Применение обновления безопасности

Миграция `SecuritySessions` добавляет только таблицу сессий, не переписывая аккаунты, пароли и персонажей. При обычном следующем запуске backend она применится автоматически. Перезапустите backend и frontend вместе. Старые cookie без серверной записи больше не принимаются: всем нужно один раз войти заново. Если ключи Data Protection потеряны при переносе сервера, тоже потребуется новый вход. Рабочую базу в ходе проверок этого обновления не использовали; миграция испытана на отдельной тестовой базе.

Поиск и публичные профили доступны только после входа. Сервер выдаёт не более 20 игроков за страницу, ограничивает строку поиска 24 символами и сортирует результат по нормализованному имени и ID. Публичный ответ содержит только ID, имя, уровень, дату регистрации и описание; email, роль, кредиты, ресурсы, характеристики и журналы отсутствуют. Заблокированные аккаунты скрыты.

Описание ограничено 300 символами. Оно хранится и отображается обычным текстом: HTML-подобные строки не исполняются браузером.

Друзья и заявки доступны только после входа. Для каждой пары игроков база допускает только одну ожидающую заявку или одну дружбу. Встречный запрос не принимает заявку автоматически: получатель увидит её во входящих. Заблокированные аккаунты скрываются из списков и недоступны для действий. В ответах есть только публичные данные: ID, имя и уровень.

Каждое игровое действие принимает `requestId`. Сервер связывает его с игроком, типом и параметрами операции. Точный повтор возвращает сохранённый итог с `replayed=true` и текущими ресурсами без повторного списания или награды; тот же ID с другими параметрами возвращает HTTP 409. Браузер хранит ID незавершённого действия локально до получения ответа, поэтому после обрыва связи нужно повторить то же действие с теми же параметрами. Перед контрактом, тренировкой и использованием предмета сервер в этой же транзакции сначала применяет восстановление ресурсов. Стоимость товара, его активность и эффект берутся из базы: клиент передаёт только ID предмета и количество от 1 до 100.

## Миграции базы

Миграции находятся в `backend/Millionnika.Api/Migrations`. При запуске backend выполняет только ещё не применённые миграции. Актуальная последовательность и назначение каждого этапа перечислены в [ARCHITECTURE](docs/ARCHITECTURE.md#миграции). Последняя миграция — `20261018175853_NpcHuntingAssignments`: она переносит прежние связи роботов с локациями в отдельную таблицу, не меняя характеристики, добычу и снимки боёв. Применённые миграции не переписывать.

`TornEquipment` добавляет определения и уникальные экземпляры экипировки; стартовые товары вставляются по фиксированным ID один раз и не перезаписывают правки администратора. Миграции ограничений проверяют старые данные и при несовместимости останавливаются без автоматического исправления.

## Уровни и Взлом

Общий уровень растёт от общего опыта, который дают успешные контракты и тренировки. Вкладка `/hacking` показывает отдельный уровень Взлома и три задачи. Успешная задача даёт оба вида опыта; провал не меняет опыт Взлома. Пороги и бонус шанса находятся только в серверной секции `Progression` файла `backend/Millionnika.Api/appsettings.json`.

На максимальном 20-м уровне опыт продолжает копиться. Обычные контракты находятся в `/contracts`; задачи Взлома используют тот же серверный маршрут, транзакцию, журнал и requestId.

Короткая проверка: войдите, откройте `/profile`, затем `/hacking`. Первая задача доступна сразу, следующие показывают требуемый уровень Взлома. После успешного выполнения обновятся награды и прогресс; точный повтор сетевого запроса не начислит их второй раз.

## Охота на роботов

Раздел `/activities` ведёт к прежнему Взлому и новой странице `/hunting`. Для охоты нужны надетое оружие, здоровье, энергия и — для Primary/Secondary — «Стандартные импульсные заряды» подходящего калибра из магазина. Сервер резервирует не более одного заряженного и трёх запасных магазинов; общий запас одного калибра нельзя одновременно выдать двум пушкам. Неиспользованные заряды возвращаются один раз при завершении.

Бой ограничен 25 действиями или пятью минутами, между командами сервер требует одну секунду. Обновление страницы не сбрасывает бой. Поражение, ничья или тайм-аут не возвращают энергию и один раз поднимают здоровье минимум до 25%. Формулы являются настраиваемым приближением «Миллионики» и описаны в [COMBAT_SPEC](docs/COMBAT_SPEC.md).

Короткая проверка:

1. В `/shop` купите оружие и, если оно стрелковое, импульсные заряды; наденьте оружие в `/inventory`.
2. Откройте `/activities` → «Охота на роботов», выберите доступную цель.
3. Выполняйте атаку или перезарядку не чаще раза в секунду; обновите страницу посреди боя и убедитесь, что ход/HP сохранились.
4. После завершения проверьте здоровье, энергию, награду и прогресс Охоты в `/profile`.
5. В `/admin` можно изменить или отключить локацию/робота с обязательной причиной; уже начатый бой сохраняет исходный снимок.

Для публичного размещения текущие HTTP-настройки не подходят. Требования к HTTPS, reverse proxy, cookie, CORS, общим ключам и нескольким экземплярам перечислены отдельно в [ARCHITECTURE](docs/ARCHITECTURE.md#https-и-будущее-размещение). Публичное размещение в текущем этапе не выполнялось.

Стартовые цены хранятся в PostgreSQL: «Нейро-снэк» — 25 кредитов, «Успокоитель» — 20, «Аптечный наногель» — 35. Эффекты также находятся в базе, а не в frontend.

## Ручная проверка безопасности

Проверки с созданием/блокировкой аккаунтов выполняйте только на отдельном тестовом экземпляре и разрешённой тестовой базе, не на рабочих игроках.

1. Зарегистрируйтесь, выполните тренировку, покупку и выход; повторный вход должен работать.
2. В двух браузерах войдите одним тестовым игроком. Выход в первом не должен завершить второй вход.
3. Тестовым администратором заблокируйте и разблокируйте игрока: оба старых входа должны перестать работать, новый вход после разблокировки — работать.
4. Повторите неверный вход больше `LoginNameLimit` раз: появится сообщение с ожиданием; после указанного времени снова можно входить.
5. Проверки отсутствующего/поддельного CSRF и повторного использования старых cookie выполняет `HttpSecurityTests`; вручную не копируйте cookie или токены в отчёты.

## Ручная проверка восстановления

1. Войдите и откройте профиль.
2. Потратьте энергию в «Имплант-центре» или хладнокровие в «Контрактах».
3. Вернитесь в профиль: рядом с неполным ресурсом идёт обратный отсчёт.
4. Закройте сайт, остановите оба процесса, подождите один интервал и снова запустите приложение.
5. После входа профиль должен показать восстановленное значение. Здоровье измениться не должно.

## Ручная проверка магазина

1. Войдите и откройте «Магазин» из профиля.
2. Купите один предмет — кредиты уменьшатся, предмет появится в «Инвентаре».
3. Предварительно потратьте нужный ресурс, затем используйте предмет.
4. Проверьте, что количество предмета уменьшилось, а ресурс вырос не выше максимума.
5. При нехватке кредитов или предметов сервер покажет отказ и ничего не спишет.

## Ручная проверка экипировки

1. Войдите и купите в `/shop` «Разрядник Искра» и одну часть комплекта техника.
2. В `/inventory` убедитесь, что каждая покупка показана отдельным экземпляром со своими рейтингами.
3. Нажмите «Экипировать», затем откройте `/profile`: вещь должна находиться только в разрешённом слоте, а Temporary — оставаться пустым.
4. Купите второй предмет того же слота и наденьте его: прежний останется в инвентаре. Нажмите «Снять» — предмет не должен исчезнуть.
5. В админке можно отключить тестовый товар: он исчезнет из магазина, но уже купленный экземпляр останется у владельца. Не меняйте рабочие данные без отдельной необходимости.

## Ручная проверка админки

1. Создайте администратора локальной командой выше и войдите под ним.
2. Откройте игрока в `/admin`, измените ресурс и обязательно укажите причину.
3. Убедитесь, что запись появилась в разделе «Изменения администратора».
4. Заблокируйте тестового игрока: его действующая сессия должна завершиться, новый вход запрещён.
5. Войдите обычным игроком и попробуйте открыть `/admin`: сайт вернёт его в профиль, а прямой запрос API получит HTTP 403.

## Ручная проверка публичных профилей

1. Войдите и откройте «Игроки» в профиле.
2. Найдите игрока по части имени и перейдите по страницам выдачи.
3. Откройте собственный публичный профиль и сохраните описание до 300 символов.
4. Для проверки безопасного текста введите, например, `<b>Текст</b>` — теги должны отображаться буквально.
5. Откройте профиль другого игрока: формы редактирования там быть не должно.

## Ручная проверка друзей

1. Создайте два обычных аккаунта в разных браузерах или один из них в приватном окне.
2. Откройте публичный профиль второго игрока и нажмите «Добавить в друзья».
3. У второго аккаунта откройте «Друзья» → «Входящие заявки» и примите заявку.
4. Убедитесь, что игрок появился у обоих в разделе «Друзья».
5. Удалите дружбу и проверьте, что запись исчезла у обоих. Там же можно проверить отмену и отклонение заявки.
