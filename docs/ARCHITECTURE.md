# Архитектура «Миллионики»

Карта фактического кода на 10 октября 2026 года. Планируемые функции не считаются реализованными. Известные ошибки и проверочные ограничения: [REVIEW.md](REVIEW.md).

## Поток запроса

Браузер загружает Next.js с localhost:3000. Клиентские страницы вызывают ASP.NET Core на localhost:5080 через fetch с `credentials: include`. Backend проверяет cookie и права, выполняет сервисную логику, использует EF Core/Npgsql для PostgreSQL на localhost:5432 и возвращает отдельный DTO. Браузер к PostgreSQL не подключается.

Next.js также делает серверные запросы для стартовых статусов и проверки роли /admin. Это не универсальный API-прокси: большинство игровых запросов идут из браузера напрямую в ASP.NET Core. `BACKEND_URL` нужен серверной части Next.js, `NEXT_PUBLIC_API_URL` попадает в клиентскую сборку. Секретов в этих переменных быть не должно.

## Сущности

| Таблица / C# | Связи и смысл |
| --- | --- |
| `users` / User | Учётная запись, нормализованные уникальные имя/email, хеш пароля, Role, IsBlocked, описание, дата. |
| `characters` / GameCharacter | Один персонаж на UserId (уникальный FK), ресурсы/максимумы, опыт, уровень, характеристики и две UTC-отметки восстановления. |
| `contracts` / Contract | Имя, стоимость, шанс, награды, активность, CooldownSeconds. Cooldown хранится, но сейчас не применяется. |
| `action_logs` / ActionLog | Много записей на пользователя; уникальный (UserId, RequestId). Результат, расход, награды, характеристика или ItemId/количество. ItemId — историческое поле, не FK на каталог. |
| `items` / Item | Каталог предметов: цена, тип, активность, описание, ресурс эффекта и величина. |
| `player_inventory` / PlayerInventoryItem | Связь персонаж–предмет с количеством; уникальный (CharacterId, ItemId), Quantity > 0. Нулевая позиция удаляется. |
| `admin_audit_logs` / AdminAuditLog | FK на администратора, действие/цель, old/new JSONB, причина и UTC. TargetId — строка, не полиморфный FK. |
| `friend_relations` / FriendRelation | Четыре FK на users: Low/High и sender/recipient. Уникальная пара Low/High; Pending или Accepted. Отмена/отказ/удаление дружбы удаляют запись, отдельной истории этих действий нет. |

Удаление User каскадно удаляет персонажа и игровые журналы, удаление персонажа — инвентарь. Ссылки аудита и дружбы ограничивают удаление пользователей. При очистке тестов важно учитывать эти связи; рабочие данные не очищать тестовыми скриптами.

## Игровые настройки

`backend/Millionnika.Api/appsettings.json` содержит `CharacterDefaults`, `Training`, `ResourceRecovery`. Начальные значения применяются при создании персонажа, а не переписывают существующих. Options-классы находятся в Configuration; проверки конфигурации при старте пока нет.

Контракт добавлен миграцией GameplayActions. Три предмета заданы через HasData в GameDbContext и миграцию NpcShopInventory. Текущие параметры каталога хранятся в БД и меняются админкой; клиент не задаёт стоимость, награды или эффект. Не переигрывать старые миграции ради изменения текущего баланса.

Восстановление вычисляется лениво при профиле, контракте, тренировке и использовании предмета. Интервалы считаются по серверному UTC; TimeProvider внедрён в ResourceRecoveryService. При расходовании полного ресурса GameActionService обновляет временную отметку, чтобы не накопить восстановление за время на максимуме. Здоровье не восстанавливается автоматически. Браузерный отсчёт лишь отображает дату и запрашивает профиль по завершении интервала.

## Авторизация и роли

Регистрация сохраняет User и Character одним SaveChanges (транзакция EF). Пароль хеширует PasswordHasher<User>. Имя/email нормализуются, уникальные индексы страхуют параллельную регистрацию.

Cookie `millionnika_session`: HttpOnly, SameSite=Lax, Secure при HTTPS-запросе, 7 дней со sliding expiration. Claims: UserId, имя, роль. OnValidatePrincipal при каждом запросе читает пользователя из БД, отклоняет отсутствующего/заблокированного и обновляет роль. `/api/admin/*` требует Admin; остальные личные API требуют входа. Списки и собственные действия берут владельца из claims, а не из пользовательского параметра.

Первый Admin создаётся интерактивной командой `dotnet run --project backend\Millionnika.Api -- --create-admin`. Пароль вводится скрыто. Команда создаёт новый аккаунт, не повышает существующий. Публичные DTO не включают роль, email и игровые ресурсы; администратор видит расширенные данные, но не пароль/хеш.

Пока нет CSRF-токенов, лимита входа и постоянного отзыва сессии — см. REVIEW. Наличие cookie в frontend proxy само по себе не доказывает авторизацию; её проверяет backend.

## Транзакции и requestId

Игровой сервис начинает транзакцию, блокирует строку персонажа через параметризованный `SELECT ... FOR UPDATE`, проверяет существующий ActionLog, валидирует серверные условия, меняет персонажа/инвентарь и пишет журнал. Коммит объединяет результат и запись requestId. Уникальный индекс (UserId, RequestId) общий для всех четырёх игровых действий. Ожидаемые отказы также запоминаются.

Восстановление внутри этой блокировки согласовано с расходом. Повторы возвращают прежний результат с текущим состоянием персонажа; проверка совпадения типа/параметров пока неполная. На клиенте новый UUID создаётся каждым нажатием, повтор после потери ответа не сохраняет прежний ключ.

AdminService блокирует изменяемую запись и сохраняет аудит вместе с изменением. Friends канонизирует два Guid, блокирует строки обоих User в одном порядке, затем читает/меняет связь. Уникальная пара предотвращает две встречные заявки. Встречная заявка возвращает incoming, не принимает её. Для друзей отдельного requestId нет; повтор не создаёт вторую связь, но ответ после удаления или принятия может быть отказом.

## Как расширять

### Добавить контракт

Сейчас интерфейс и сервис рассчитаны на ровно один активный контракт. Создать второй активный только записью БД нельзя: Single/SingleOrDefault выбросят исключение. Для каталога потребуется отдельный этап: список DTO, выбор ContractId, серверная проверка активности/стоимости, определённая семантика requestId и соответствующий интерфейс/тесты. Новый контракт вводить отдельной миграцией данных; существующие параметры можно редактировать через Admin API. Создания контракта в админке пока нет.

### Добавить предмет

Для существующего типа `consumable` и эффекта energy/nerve/health добавить уникальный ID, имя, описание, цену и эффект в модель стартовых данных и новую миграцию. UI магазина/инвентаря читает каталог и не требует зашивать предмет. Для нового эффекта расширить серверный обработчик InventoryService и AdminRules, DTO при необходимости, добавить проверки максимума, отсутствия предмета, атомарности и повторов. Создания предмета в админке пока нет.

### Добавить игровую механику

Определить DTO и интерфейс сервиса, серверные правила и конфигурацию, зарегистрировать DI и маршруты в Program.cs. Для изменения ресурсов использовать тот же порядок блокировок и общую транзакцию с журналом; не обходить ActionLog/requestId. Если действие затрагивает несколько игроков, сначала определить единый порядок блокировок. Изменение модели требует новой миграции и согласованного snapshot; клиент получает только необходимые DTO. Добавлять модульные проверки правил, PostgreSQL-проверки параллельности и HTTP-проверки прав/CSRF. Сначала учитывать нерешённые ошибки REVIEW.

## Запуск, тесты и миграции

Рабочие команды и безопасная подготовка отдельной тестовой базы приведены в [README](../README.md). Интеграционные тесты требуют `MILLIONNIKA_TEST_CONNECTION_STRING`. Без неё или с недопустимым именем базы/адресом/пользователем fixture завершится ошибкой до соединения. User Secrets и обычная строка приложения не читаются тестами.

Единая DatabaseFixture коллекции PostgreSQL integration применяет миграции до четырёх интеграционных классов. Предварительный запуск backend не нужен. Классы коллекции последовательны, Task.WhenAll внутри тестов по-прежнему создаёт параллельные запросы. Разные процессы тестирования должны использовать разные тестовые базы. 79 тестов не включают полноценный браузерный E2E-набор.

Backend автоматически вызывает MigrateAsync при старте и применяет отсутствующие записи из `__EFMigrationsHistory`. Последовательность: InitialAccounts → GameplayActions → ResourceRecovery → NpcShopInventory → AdminMvp → PublicPlayerProfiles → Friends. Прикладной пользователь владеет БД, поэтому может выполнять DDL. В production это следует отделить от runtime-прав.

В текущем окружении команды dotnet-ef нет. Миграции и Designer/snapshot в проекте поддерживались вручную; поздние модели вызывают BuildModel предыдущих миграций. Не редактировать применённые миграции и не сбрасывать БД. При будущем использовании генератора установить отдельно согласованную совместимую версию инструмента, проверить сгенерированную разницу и испытать новую миграцию на отдельной базе. Изменение HasData может перезаписать настройки администратора — такие миграции требуют внимательной проверки.

## Ограничения

- Один серверный проект, прямой доступ сервисов к EF Core; отдельного доменного слоя, очередей, Redis и фоновых персональных таймеров нет.
- Опыт начисляется, но повышения уровня нет. Поле Level само по себе не означает систему уровней.
- Один контракт, без действующего cooldown; нет сообщений, уведомлений в реальном времени, синдикатов, чата, рынка и рейтинга.
- Админка редактирует существующий каталог; создание каталога, новости и редактирование таймеров через UI отсутствуют.
- Нет общего HTTP-обработчика безопасных ошибок, полного валидационного слоя конфигурации, серверного отзыва cookie и защиты арифметики от всех переполнений.
- Подготовка схемы тестов согласована в одном процессе; нагрузочная проверка и стратегия нескольких экземпляров приложения пока отсутствуют.
- История Git начата `76f8c45`; `eb58348` убрал `.verification` из отслеживания, оставив локальные файлы. Старые сборки остаются в первоначальном коммите, история не переписывалась.
