## Подтверждённые проблемы

### R01 — P1: нет полноценной защиты изменяющих запросов от CSRF

**Исправлено:** единая IAntiforgery-проверка небезопасных методов и общий apiFetch с X-CSRF-Token. Исходное воспроизведение ниже сохранено как история.

Файлы: `backend/Millionnika.Api/Program.cs:49`, `Friends/FriendEndpoints.cs`, `Auth/AuthEndpoints.cs:15`.

Cookie имеет `SameSite=Lax`, CORS допускает только `http://localhost:3000`, но нет antiforgery-токена и серверной проверки Origin. Запрос принятия заявки не требует JSON-тела. В тесте POST `/api/friends/requests/{id}/accept` с cookie получателя и посторонним `Origin: http://localhost:3999` успешно принял заявку без токена.

Условия угрозы: страница другого origin в пределах того же site, например другой порт localhost или подконтрольный атакующему соседний поддомен при будущем размещении. SameSite не разделяет порты; простой POST не требует CORS-preflight, а запрет чтения ответа не отменяет действие. Для произвольного внешнего site Lax обычно не передаст cookie в таком POST; обход этой защиты не заявляется. Проверен HTTP-запрос с заданными заголовками, полноценный браузерный exploit не запускался.

Исправление: единая серверная CSRF-защита всех POST/PUT/DELETE, включая logout и действия без тела; согласованный токен в клиенте либо строго проверяемые Origin/Fetch Metadata с определённой политикой отсутствующих заголовков. CORS оставить отдельной защитой чтения ответов.

### R02 — P1: отсутствует ограничение попыток входа

**Исправлено для одного экземпляра:** конфигурационные временные лимиты IP входа/регистрации и нормализованного логина; 429 с Retry-After. Ограничение нескольких экземпляров указано ниже.

Файлы: `Program.cs`, `Auth/AuthEndpoints.cs:14`, `Auth/AuthService.cs`.

Выполнено 25 последовательных неверных входов в существующий тестовый аккаунт: все вернули 401, ни одного 429 или временной блокировки. В коде нет rate limiter, счётчика ошибок или задержки по аккаунту/IP. Регистрация также не ограничена по частоте.

Исправление: ограничение по IP и нормализованному логину, временная задержка/блокировка, безопасные одинаковые ответы и HTTP-тесты лимитов. Не превращать это в постоянную блокировку, которую может навязать посторонний.

### R03 — P1: cookie не отзывается окончательно

**Исправлено:** серверные UserSession в PostgreSQL, удаление текущей при выходе и всех при блокировке; прежние cookie после разблокировки не восстанавливаются.

Файлы: `Auth/AuthEndpoints.cs:69`, `Program.cs:63`, `Entities/User.cs`.

Воспроизведение: сохранить cookie, выполнить logout, отправить сохранённую cookie повторно — `/api/profile` возвращает 200. При административной блокировке запрос получает 401 и новый вход запрещён, но после разблокировки прежняя сохранённая cookie снова получает 200 без нового входа. Logout удаляет cookie у браузера, а серверного состояния отзыва нет.

Исправление: версия сессий/security stamp пользователя или серверное хранилище сессий. Менять версию при блокировке, отзывать конкретную сессию при выходе; проверять её на каждом запросе. Особенно важно для ранее скопированных cookie.

### R04 — P1: переполнение делает кредиты отрицательными

**Исправлено.** Единые пределы, проверяемая арифметика, серверная/административная валидация и ограничения PostgreSQL добавлены. Миграция сначала проверяет существующие данные и ничего не исправляет автоматически. Доказательства приведены в конце.

Файлы: `Admin/AdminRules.cs`, `Game/GameActionService.cs:68`, `Game/GameRules.cs`, `Data/GameDbContext.cs`.

Через разрешённый API администратора задать кредиты `9223372036854775807`, активный контракт с шансом 1 и наградой 50, выполнить контракт. Получено `-9223372036854775759` кредитов. Это не обычное расходование и требует большого значения, разрешённого администратору. Сложение C# выполняется без проверки переполнения; CHECK на неотрицательные значения персонажа отсутствует. Аналогичный класс риска есть у опыта и характеристик.

Исправление: разумные верхние границы конфигурации/админки, проверяемая арифметика до изменения состояния, понятный отказ с откатом транзакции и ограничения БД. Учесть безопасный диапазон целых JavaScript при передаче `long` в JSON.

### R05 — P1: тесты по умолчанию используют рабочую базу

**Исправлено.** Текущий код требует `MILLIONNIKA_TEST_CONNECTION_STRING`; fallback удалён. Проверка разрешённого имени локальной базы выполняется до подключения. Детали проверки — ниже.

Файлы: `Millionnika.Api.Tests/Inventory/InventoryServiceIntegrationTests.cs:266`, `Admin/AdminAuditIntegrationTests.cs:86`, `Players/PlayerDirectoryIntegrationTests.cs:146`, `Friends/FriendServiceIntegrationTests.cs:200`; прежняя инструкция тестов README.

Тесты выполняют миграции, создают и удаляют записи. Есть фиксированные имена `AuditAdmin`/`AuditPlayer`, которые могут конфликтовать с настоящими аккаунтами. ### R06 — P2: гонка миграций на пустой тестовой базе

**Исправлено.** Одна DatabaseFixture коллекции PostgreSQL integration применяет миграции до всех четырёх интеграционных классов. Внутритестовые параллельные запросы сохранены.

Файлы: те же четыре интеграционных набора; вызовы `MigrateAsync` в отдельных классах.

Первый параллельный запуск тестов на новой базе дал 3 ошибки PostgreSQL: `42P07` (таблица contracts уже существует) и `42701` (CreditsSpent уже существует). После подготовки схемы все 67 проходят. Только Inventory имеет собственный Lazy для миграции; общей координации всех классов нет.

Исправление: один этап миграции/общая fixture перед параллельными тестами. Сохранять параллельность самих игровых запросов, которую тесты должны проверять.

### R07 — P2: отключение последнего контракта приводит к HTTP 500

**Исправлено.** Отсутствующий, отключённый или некорректный контракт возвращает ожидаемый отказ без исключения, списания и награды. Интерфейс явно показывает отсутствие активного контракта. Доказательства приведены в конце.

Файлы: `Game/GameActionService.cs:49`, `Admin/AdminService.cs:83`, `frontend/app/contracts/page.tsx`.

Администратор отключает единственный контракт. Повторный POST из ранее открытой страницы вызывает `SingleAsync(candidate => candidate.IsActive)` и возвращает 500. GET корректно возвращает 404 при отсутствии активного контракта. Если добавить два активных контракта, Single/SingleOrDefault также не поддерживают такой набор; это ограничение расширения, а не реализованный каталог.

Исправление: явная обработка недоступного контракта без исключения; перед расширением добавить выбор по ID и список. Ожидаемый отказ и ресурс должны сохраняться согласованно с политикой requestId.

### R08 — P2: нулевая стоимость разрешена админкой, но контракт не выполняется

**Исправлено.** Для прототипа стоимость строго больше нуля в игровой логике, Admin API, форме и CHECK PostgreSQL. Ноль и отрицательные значения отклоняются.

Файлы: `Admin/AdminRules.cs`, `Game/GameRules.cs` (`HasEnoughResource`), `frontend/app/admin/page.tsx:98`.

PUT контракта с `costNerve=0` возвращает 200. Выполнение при полном хладнокровии возвращает 409 «Недостаточно хладнокровия», поскольку игровая проверка требует `cost > 0`.

Исправление: согласовать правило — либо запретить нулевую стоимость на всех уровнях, либо корректно поддержать бесплатный контракт.

### R09 — P2: requestId не привязан к содержимому операции

Файлы: `Game/GameActionService.cs:41,95`, `Inventory/InventoryService.cs` (`ReplayAsync`); страницы контрактов, тренировок, магазина, инвентаря.

После покупки отправить её requestId в тренировку: API отвечает успешным результатом покупки, тренировка не происходит. GameActionService не проверяет ActionType. Inventory проверяет тип, но не совпадение ItemId/количества. Повтор тренировки с другой характеристикой также возвращает прежнее действие. Двойного начисления при этом не обнаружено, проблема — ложное подтверждение другого намерения.

Клиент создаёт новый UUID при каждом нажатии. Если ответ потерян после успешного коммита, повторное нажатие станет новым действием и повторно спишет ресурс.

Исправление: сохранять тип и нормализованные параметры/хеш запроса, отклонять несовпадающий повтор; хранить на клиенте ID незавершённого действия до выяснения его результата. Ответы повторов сейчас сочетают прежний итог с текущими ресурсами — это следует явно определить в контракте API.

### R10 — P2: административный аудит неполон

Файлы: `Admin/AdminService.cs:67,73,166`, `Admin/AdminBootstrapper.cs:63`.

Блокировки, изменение ресурсов, контрактов и предметов записывают администратора, цель, причину, старые/новые основные значения и UTC-дату в той же транзакции. Это подтверждено HTTP и тестом.

Но изменение ресурсов также сбрасывает обе отметки восстановления, а в OldValue/NewValue есть только кредиты, энергия, хладнокровие, здоровье. Даже сохранение тех же чисел изменяет прогресс восстановления без отражения в аудите. Локальное создание Admin вообще не создаёт запись аудита (подтверждено кодом; интерактивную команду в этом обзоре не запускали).

Исправление: включить меняемые временные отметки в аудит, определить событие локального создания администратора с безопасным обозначением исполнителя. Не писать туда пароль/хеш.

### R11 — P2: диагностический ответ 500 раскрывает заголовки в Development

Файлы: `Properties/launchSettings.json`, `Program.cs`, исключение R07.

Запуск по README использует Development и HTTP. При R07 тело ответа содержит stack trace, пути и `Cookie: millionnika_session=...`. Значение cookie не сохранено в отчёте. Это не доказательство доступа к чужой сессии: ответ получает вызывающий пользователь, но пересылка диагностики может раскрыть его секрет.

Исправление перед размещением: Production, централизованные безопасные ошибки без отражения заголовков, HTTPS и соответствующая Secure-cookie/настройка прокси. Режим разработки оставить только для локальной диагностики. CORS сейчас жёстко привязан к localhost:3000.

### R12 — P2: после удаления последнего элемента страницы друзей пропадает навигация

Файл: `frontend/app/friends/page.tsx:33,47,87`.

Условия по коду: 21 запись, открыта страница 2, единственная запись удалена. `load()` снова запрашивает страницу 2; остаётся 20 записей и totalPages=1. Список пуст, а блок навигации скрыт условием `totalPages > 1`. Пользователь не может перейти на первую страницу без перезагрузки.

Исправление: после изменения списка ограничивать текущий номер максимумом страниц и загружать допустимую страницу. Подтверждено анализом перехода состояний; отдельный браузерный прогон с 21 записью не выполнялся.

### R13 — P1 для сохранности проекта: история Git отсутствует

**Исправлено после обзора.** Пользователь создал `76f8c45`. Очистка индекса отдельным коммитом `eb58348` исключила `.verification` (97 файлов результатов сборки); локальные файлы сохранены. Старый коммит по-прежнему содержит эти результаты: история намеренно не переписывалась.

## Результат исправления R09–R12 — 2026-10-10

- **R09 исправлен.** `ActionLog.RequestSignature` связывает requestId с игроком (уникальный индекс), типом и нормализованными параметрами. Точный повтор возвращает сохранённый итог с `replayed=true` и текущим состоянием без второго изменения. Тот же ID для другого типа, предмета, количества или характеристики возвращает HTTP 409 без списаний/начислений. Frontend хранит незавершённые ID и параметры в localStorage до получения любого HTTP-ответа; сетевой обрыв оставляет их для безопасного повтора.
- **R10 исправлен.** Админское сохранение неизменённых энергии/хладнокровия больше не двигает отметки восстановления. Обе отметки входят в старое и новое значение аудита. Локальное создание администратора пишет `admin_created` в той же операции; запись содержит ID/роль, но не пароль, хеш или email.
- **R11 исправлен.** Общий middleware возвращает для необработанной ошибки только безопасное сообщение и случайный `errorId`. В журнал уходит ID и тип исключения без объекта исключения, заголовков, cookie, stack trace и локальных путей. Настройки HTTPS/прокси для будущего размещения документированы; публичное размещение не выполнялось.
- **R12 исправлен.** Сервер ограничивает запрошенную страницу последней существующей, а интерфейс принимает исправленный номер. Интеграционный сценарий 21 дружба → страница 2 → удаление единственной записи вернул страницу 1 с 20 записями.
- Миграция `BindRequestIdToOperation` заполняет сигнатуры существующих журналов и добавляет CHECK непустого значения. На отдельной тестовой базе полный прогон: **137/137**, 0 пропусков. Backend Release и frontend production-сборка прошли без ошибок.
- Рабочая база и реальные аккаунты на этом шаге ещё не изменялись. Применение описывается отдельной записью STATUS после резервного копирования и проверки совместимости.

## Необязательные улучшения и архитектурные ограничения

- Валидировать `CharacterDefaults`, `Training`, `ResourceRecovery` при старте. Сейчас ошибочная серверная конфигурация обнаруживается поздно или создаёт недопустимое исходное состояние; пользователь не может менять её через обычный API.
- Добавить постраничный просмотр административных журналов: сейчас API возвращает только последние 100, хотя старые записи сохраняются.
- Для дальнейшего роста усилить CHECK-ограничения пары друзей: сейчас канонический порядок и согласованность sender/recipient обеспечены сервисом, а БД проверяет уникальность пары, разные ID и допустимый Status.
- Выделить миграционные права и runtime-роль перед production: сейчас приложение не postgres, но владеет схемой и применяет DDL при запуске.
- Зафиксировать транзитивные NuGet-зависимости lock-файлом. npm имеет package-lock, версии прямых NuGet-пакетов фиксированы, packages.lock.json отсутствует.
- Health проверяет `SELECT 1`, но не готовность схемы. Некоторые ошибки миграций логируются, после чего сервер продолжает стартовать.
- Новая UI/E2E-регрессия полезна: текущие 67 тестов в основном проверяют правила и сервисы, не полный HTTP middleware и браузер. Название AdminAuthorizationTests не означает тестирование реальных маршрутов — там отдельно проверяется RolesAuthorizationRequirement.
